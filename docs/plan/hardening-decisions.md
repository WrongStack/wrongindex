# Integration hardening decisions (2026-11-11)

These updates supplement the original ADRs and retain INV-01..INV-14. They describe the implementation in this working session; validation results and remaining acceptance gates are recorded in `docs/status.md`.

## WI-ADR-015 — Revalidate Git trust per file

Current WrongStack `a6211d4792ce` no longer discards an otherwise usable generation because an unrelated worktree entry changed. WrongIndex now reads one isolated Git listing immediately before assigning new clean-blob stamps. Only a file whose original clean blob still matches receives a new stamp. A changed or unverifiable file gets no new trust; a previously trusted file whose new stamp cannot be vouched for has its stamp cleared as WrongStack does. Discovery completeness and authoritative deletion rules remain unchanged.

This updates the whole-checkout retry default in the original indexing pipeline and compatibility prose. A deterministic scan -> unrelated edit -> publication test failed with `SourceChanged` before the patch and passes afterwards; a changed indexed-file control receives no trust. Old contract fixtures remain intact. The current-source snapshot is separate from the original baseline, and a required source-drift gate fails on added, removed or changed contract files.

Baseline review addendum (2026-11-11): local WrongStack main advanced from `a6211d4792ce` to `198aade0b7e6` during verification. The only recorded contract-scope change is the TUI stream-flush timer/comment, with no indexer consumer. A separately generated 280-file snapshot records this accepted baseline; original snapshots remain unchanged. CI initially referenced a621 while it was the published remote baseline. When remote main subsequently advanced to the already-reviewed 198 commit, the next artifact run correctly refused the old fingerprint. CI and artifact workflows now reference the existing generated 198 snapshot. No generated fixture was edited and no native/query/storage semantic acceptance is inferred from the pointer change. This review neither publishes the other contributor's commit nor relabels a delegation-overlay run as clean-commit certification.

Producer review addendum (2026-11-12, WI-ADR-015): WrongStack 1.6.0 main is `9ec93ad7f306ffb354ac4f6905402915c66999cf`. Immutable scope inspection records 282 files, 14 changed and two added against 198; no removed files. The scoped indexer/store admission matches the earlier recorded delegation overlay; the owner-lock differences are formatting, while client/publication/service changes are reviewed as the previously tested transport and cache-coherence integration. Shared terminal/price-cliff utilities and version metadata do not change index storage semantics; CLI materialization events enqueue bounded in-root reindex notifications. A separate clean archive and script-generated baseline retain the original snapshots. Fifteen generated full/incremental/targeted differential cases pass against this exact producer; the current working-tree adapter (including its separate shutdown mapping) passes 37 focused tests in each of five runs. This is not full WrongStack monorepo certification.

The service compatibility worker retains mandatory scoped delegation for a guarded producer. Direct reference indexing in differential tests instead uses a dedicated fixture-only entry, requiring recorded provenance, temporary `.tmp` roots and an index without an ownership lock; it never grants service delegation or opens a live owned index. This corrects test setup for a producer which now exposes the delegation API, without weakening production ownership checks or changing a generated parity fixture.

## WI-ADR-016 — Native verified byte bridge for Windows JS clients

Bun and Node clients use a hidden `wrongindexd --ipc-bridge --data-root <root>` transport. The daemon publishes its absolute executable path as optional `clientBridge` discovery metadata. The bridge uses the existing Rust pipe connector, verifying the SID of the server on the exact connected handle before forwarding stdin. Credentials travel only through private native/JS memory and pipes, never arguments, logs, responses or the WebView.

This adds a transport process per active JS connection (at most three per adapter host: one control lane and two read lanes). They are client-owned byte brokers, not indexing daemons; closing a stream terminates its broker. This process and memory cost must be counted in installed-product measurements. It avoids adding a separate native addon or runtime-specific FFI dependency. The indexing engine and per-user service topology are unchanged.

Old Rust clients remain wire compatible. The hardened JS adapter requires a matching daemon build that publishes the bridge; it refuses older discovery with `PROTOCOL_UNSUPPORTED` and never falls back to sending a token through an unverified Windows socket. Deploy the daemon and adapter together. No minimum published release is claimed until the corresponding artifact exists.

Handshake, response and queued-request waits are bounded. Deadline expiry or explicit close rejects pending work and terminates that stream so a late reply cannot satisfy a later request. Only read operations are automatically retried after an ambiguous disconnect; mutation admission is never blindly replayed. The client queue is capped at 128 requests per connection.

## WI-ADR-017 — Publication metadata and cache updates

Daemon query replies carry generation/stamp, instance, observation time, indexing and freshness. The adapter keeps metadata in an internal WeakMap without changing existing JSON/model-facing query payloads. Pending or damaged publications are refused; responses from a superseded generation or retired instance are rejected. The host's existing index-state notification boundary receives publication changes. WebUI invalidation observes external identity changes even when a fast run's indexing phase was never observed.

Active watch leases poll status on their dedicated control lane once per second with at most one outstanding poll per project. This is an explicit initial policy; event-stream subscription can replace it after equivalent gap/reconnect tests. Polling continues through outages, and release/shutdown prevents a late lease acquisition from reviving a closed session. The bounded state cache tracks 128 index identities. Two separate read lanes prevent slow queries from occupying the control lane.

## WI-ADR-018 — Bound native work before tuning concurrency

Native query admission is capped at four concurrent operations, with the permit retained by actual blocking SQL work even if its caller disappears. SQLite VM work has a 30-second execution budget using the existing pinned rusqlite crate's `hooks` feature; expiration maps to `DEADLINE_EXCEEDED`. This bounds SQLite execution, not every Rust computation or a deadline/cancellation protocol for arbitrary query code.

Active indexing-job admission conservatively reserves the larger native/compatibility per-run memory cap and limits parallel jobs to half physical RAM (2 GiB minimum), up to the user's requested concurrency. A per-run cap is also clamped to that budget. Retained compatibility-worker memory, daemon/query/SQLite memory, transport brokers and GUI memory are separate costs; this reservation policy is not a hard cap on total installed-product RSS.

The daemon divides parser slots across admitted job capacity, leaving one logical CPU when possible. A shared permit gate inside each native child covers in-process parsing and all concurrent helper chunk families. The outer process-tree Job Object memory and lifetime controls remain active. Already running jobs drain when admission is reduced. Effective job and memory limits are exposed by `daemon.metrics`.

Resource and latency acceptance requires actual measurements. S/M/L benchmark and soak results must retain corpus, machine, source/binary identity and measurement boundaries. No new speedup or 24-hour reliability claim follows from the code changes alone.

Cached adapter operations use the daemon's existing atomic ownership/run-guard admission rather than synchronously probing the held lock before every request. The latter imposed a reproducible 50 ms `Atomics.wait` on each query. Ordinary local writers still use the OS lock guard. A remote ownership refusal evicts cached registration and is visible to the caller; the next explicit operation re-runs admission. Mutations are not silently replayed. Automatic synchronous route selection retains its existing local ownership check.

## WI-ADR-019 — GPUI native desktop client

The explicit user request supersedes WI-ADR-008's Tauri-only framework choice for new desktop work. Add a separate Windows GPUI client, pinned to published `gpui =0.2.2`, edition 2024 and the existing Rust 1.93 toolchain. Keep authenticated Rust IPC, read-only preview and daemon ownership/lifetime boundaries. The UI runs no project code, holds no SQLite writer and receives no token-bearing view model.

A bounded client actor handles blocking/async work away from the UI thread. Channels admit 32 commands and eight snapshots; calls and connects have finite deadlines. The view labels disconnected/stale snapshots and waits for command receipts instead of showing optimistic success. Closing the GUI drops only the client; it never sends daemon shutdown. A source client does not replace the existing installer until packaging, tray/search/update parity and manual accessibility/DPI acceptance are explicitly completed.

## WI-ADR-020 — Scoped supervised compatibility writes

Current WrongStack's cooperative owner guard also blocks the compatibility worker. Only the direct child of the lock-owning daemon may enter an async write scope for the exact canonical index directory, daemon instance and ownership epoch sent over its private supervisor pipe. WrongStack verifies the live OS lock, parent PID and matching descriptor; the descriptor alone grants nothing. Ownership detection stays true inside the scope, unrelated paths remain blocked, each admission rechecks the epoch, and scope completion revokes async descendants even on failure.

The daemon validates the registry fence and retains its run guard for the whole worker request; ownership cannot be released while it writes. Its Job Object kills the child tree if the supervisor exits. Worker stores close inside the scope. This is a cooperative ownership protocol, not protection against hostile same-user programs opening SQLite directly. There is no environment-wide bypass. Guarded engines without the API fail before opening a mutable store; native remains the default. The original current-commit oracle stays unchanged. Compatibility tests against this pending WrongStack change use a distinct archive with a recorded three-file SHA-256 overlay, never masquerading as commit-only certification.

## WI-ADR-021 — A missing or failing helper degrades per file (2026-11-12)

User request, 2026-11-12: one service on a machine indexes every registered project, in every language, without a project failing as a whole. The earlier profile refused a whole project when Bun or Node.js was absent and the project held one tree-sitter-language file (a `build.sh`, a `.h`, a `Gemfile`), when one file could not be read, or when a helper program failed on one chunk. A system-wide scan reproduced each of these with the 0.2.0 candidate.

The native writer now degrades the way WrongStack's own parsers do, and says so in the job result:

- **No Bun or Node.js, or the tree-sitter program cannot be set up or fails on a chunk:** the ten tree-sitter languages go to the regex extractor, which is what `tree-sitter-parser.ts` does when a grammar cannot be loaded. Python and Go already did this without their toolchains; a Python or Go helper that fails on a chunk, and a Go program that cannot be built, now do too. After the first failed chunk of a route the helper is not started again in that run (WI-604: no timeout per chunk).
- **TS/JS files the in-process parser refuses, with no runtime to run WrongStack's TypeScript parser:** no other parser exists for them. They get no rows in that run and keep their previous rows (INV-05); the job result lists them (`unparsedFiles`).
- **A file that cannot be read** (in use by another program, access denied): a per-file failure as in `readBatchFiles`. No rows are written for it, its previous rows stay, the job result lists it (`unreadableFiles`). A file that is gone between discovery and the read is not part of the project.
- **INV-05 for both lists.** A file listed under `unreadableFiles` or `unparsedFiles` has rows older than the file. The project's freshness is `degraded` and its `lastError` says how many files are affected until a run indexes them: a whole-project run that reports none, or a targeted run of those paths that reports none. The watcher asks for those paths again after 30 s, doubling per run that still leaves them out, up to 15 minutes; closing a file makes no change event, so without this a released file would wait for the periodic reconciliation.
- **A project with nothing to index yet:** an empty index of the baseline schema. It is not byte-identical to WrongStack's empty index: the native writer also writes `graph_stamp` metadata and `sqlite_stat1` (WI-ORACLE-01 records this DIFFERENCE against the clean `9ec93ad7f` oracle; both have zero files and symbols). Refusing it counted as a failing project, parked its watcher after eight attempts and left its first file waiting for the 15-minute probe.

`degraded` in the job result names what ran in a reduced way. It does not change freshness: successfully parsed fallback rows are current for this machine's route. The note stays in the job result, and `wrongindex doctor` lists the missing helpers. Missing Python/Go use the producer's regex route; persistent Python failure has the deliberate native extension recorded below. Tree-sitter fallback follows the producer's regex implementation, but a matching grammar-failure comparison remains unverified. The output is not the index of a machine with every helper working, and unchanged files are not re-parsed when a helper is installed later - a rebuild does that. This updates certification section 1, which had "refused and nothing is written".

**Strict mode keeps the certified behavior where exact parity is available.** When WrongStack's own engine is configured and the backend is `auto`, the service starts the native child with `WRONGINDEX_NATIVE_STRICT`: a missing or failing helper, TS/JS files without a parser and an empty project are refused as before and WrongStack's engine takes the project. A file that cannot be read is a per-file failure in both modes (it never was delegated: before, the run failed with `INTERNAL`), as in WrongStack's own `readBatchFiles`. Without that engine there is nothing to delegate to and a refusal only means no index.

Proofs: `parse::treesitter::tests`, `parse::py::tests::a_failing_interpreter_degrades_to_the_regex_extractor`, `native::tests::{a_file_in_use_does_not_fail_the_project, a_file_in_use_keeps_its_previous_rows, an_empty_project_gets_an_empty_index}`, `wrongindexd/tests/single_instance.rs`. No contract fixture changed; with every helper present the output is unchanged (the recorded oracle tests pass).

Clean-producer follow-up (2026-11-12): fifteen generated differential cases pass against immutable WrongStack 1.6.0 `9ec93ad7f306ffb354ac4f6905402915c66999cf`. Empty-project initialization was compared separately and is **DIFFERENT**: native adds `graph_stamp` and `sqlite_stat1` data; the reference does not. The empty native generation is the explicit watcher initialization extension above, not an exact-parity claim. The test-only oracle writer accepts only disposable system-temp `.tmp*` fixtures, requires recorded producer provenance and refuses ownership locks; the production compatibility worker's scoped delegation admission is unchanged.

WI-ORACLE-02 separates two helper conditions. Python/Go absent versus working controls match all logical tables in eight fresh/targeted/reconcile/unchanged comparisons. A persistently failing Python program is different: native regex extraction keeps symbols that the producer's per-file failed AST route omits (nine versus six in the fixture). The existing standalone fallback is an explicit extension in this condition; the broad statement above about matching the producer does not cover persistent helper failure. Strict `auto` mode with a configured producer uses the compatibility worker and matches it in three independent real-service runs. Tree-sitter runtime/grammar failure and locked-file reference comparisons remain NOT RUN. No parser policy or contract fixture was changed for these observations.

## WI-ADR-022 — One service, many projects: the guard, discovery and schedules (2026-11-12)

- **The endpoint is held until the service is done.** The first pipe instance is the singleton guard (WI-ADR-002/007). It was dropped when the accept loop ended, so during the drain (up to `--drain-seconds`, longer behind a compatibility-worker call) a second service could start on the same data root, mark the first one's running jobs interrupted and contend for every index. The accept loop now runs through the drain; discovery is retracted while the endpoint is still held and the endpoint goes right after it.
- **A draining service takes no new session.** It answers an authenticated connection with `SHUTTING_DOWN`, so no client takes it for a running service. `wrongindex daemon start` waits for it to go and starts a new one (the job it was finishing ends `succeeded`, not interrupted); `daemon stop` waits for it; `daemon status` reports it (exit 3); the desktop's Start says the service is shutting down instead of "already running". The WrongStack adapter maps `SHUTTING_DOWN` at authentication to `WrongIndexUnavailableError`, the class a closed endpoint produced before, so its existing fallback rules apply unchanged (the local engine only where the service does not hold the index). An adapter without that mapping sees a `WrongIndexRemoteError` for the length of a drain and does not fall back in that window: deploy the daemon and the adapter together, as WI-ADR-016 already requires.
- **One endpoint name per directory.** The name was a hash of the data root as spelled; a trailing separator, `.`/`..`, a junction, a `subst` drive or an 8.3 name gave another name and so a second service on the same registry. It is now a hash of the root as the file system resolves it (the deepest existing ancestor, the rest as written), which is the old name for an ordinary path. Only the service and `doctor` compute it; clients read it from `endpoint.json`.
- **Discovery is re-published.** Clients find the service only through its discovery files. The process that holds the endpoint checks them every five seconds and publishes them again when they are gone or name another instance.
- **Periodic reconciliation reaches every project.** One reconciliation was admitted per one-minute round, for the first due project in registration order; with the 15-minute period, projects beyond about the sixteenth were never reached, and periodic reconciliation is the only net under missed watch events. Due projects are now taken longest-overdue first, and a round admits as many as it takes for every watched project to have its turn within one period (one while there are at most as many projects as rounds in a period).
- **A change notification dropped at the full event queue** set a flag that was only read when that project's next event arrived. The supervisor now sweeps the flags every second and reconciles the flagged projects.
- **Detach.** A detached project's watch state (watcher, pending paths, in-flight batch) is dropped; before, its watcher stayed and every later edit was dispatched to a project that no longer existed, every 50 ms. A detach that is refused for an active job is refused before ownership is released. A batch admitted before a detach no longer settles against the dirty set of the next attach.
- **A restart is not an ownership transfer.** Every start took back each owned index through the full claim, including the pre-transfer backup (compatibility section 6.2): a `VACUUM INTO` copy of every index before the service accepted a client (10 real checkouts: 8.5 s; 4 s and 212 MB for the WrongStack index alone), and with `backupKeep` 3 the backup of a real transfer was gone after three restarts. A service now marks each index it releases at shutdown (`.wrongindex-released.json`: its data root, the epoch, length and modification time of `index.db` and `-wal`, written while the lock is still held). A claim at the next epoch by the same data root with the files exactly as marked takes no backup; anything else - another service, a skipped epoch, any write through SQLite since, a maintenance claim, no mark - takes one as before. An explicit `ownership.release` is a hand-over and leaves no mark: the claim after it backs the index up, as `backup_restore.rs` requires. An empty `-wal` counts as none (the read-only admission check leaves one; a WAL holds nothing before its header). The ownership evidence records `backupReason`. Measured on the 10 checkouts: restore 0.8 to 1.8 s, no copies on three restarts, a backup with the change after an external write.
- **A handshake has a deadline.** A service holds its endpoint from its start, before it accepts a client, and the Rust client (CLI, desktop, GPUI) waited for the handshake reply without a bound: `daemon status` against an endpoint that accepted and never answered was still waiting when killed after 45 s, and neither `--wait-seconds` nor the desktop's 15 s for Start could take effect. The whole handshake is now bounded by 20 s and ends as "not running" with the reason; the JS adapter already bounded it.
- **A failed start says why.** A detached service has no console, and its log is opened only once its data root is usable: when the start failed before that (a data root that is a file, or one created by an elevated process that the service now refuses), `daemon start` pointed to a log that did not exist. The service leaves the reason in the user's temporary folder (`wrongindexd-start-error-<endpoint hash>.txt`, outside the data root), removes it once a later start is ready, and the CLI and the desktop's Start show it.
- **Shutdown keeps the lock of a run still writing (INV-01).** The shutdown release took every guard, whatever was running. A run that outlived the drain budget - an in-process restore, backup or check on the blocking pool, which the runtime waits for at exit - could then write the index with its lock already released. Shutdown now waits up to 5 s more for runs in flight, releases the idle projects, and keeps the lock of a project still running work; the OS releases it with the process, after the work and the native children (killed with their tasks) are gone. Such a project stays recorded as owned, as after a crash: the next start does not trust it and, without a release mark, backs the index up.
- **A slow checkout root holds back no other project.** The watcher supervisor checked every watched project's root itself, every second, on the async runtime. One check of an unreachable network path took about 2.5 s here, so one such root delayed the edits of every project by that much each round (measured with a debug hook holding one root's check for 3 s: admission p50 3.6 s, worst 8.9 s, instead of 0.43 s). Root checks now run on a thread of their own per project (not the blocking pool, which SQLite work needs; at most one per project and no other cap: a first version capped them at 16 in all, spent in registration order every round, which left every project past the sixteenth unchecked and so never watched), and a round waits at most 100 ms in all for the ones it started, else goes on with the last answer; a project whose root has never answered is not attached yet. A root that has not answered within 10 s, or answered later than that, is unavailable (`root_unavailable`), so a root that answers that slowly is not watched and given up in turn with a full reconciliation each time. Taking ownership for watching (which may back the index up, seconds for a large one) and attaching a watcher (the file-system probe, the watcher's directory handle and change request, `.gitignore`) run off the supervisor too, in a task per project (two claims at a time, so backups leave the blocking pool to the registry) with the attach on a thread of its own: a round waits at most 200 ms in all for the attaches it started, so an ordinary root is still attached in the round that decided it, and a slow one is taken up in a later round. The checks inside event handling (a changed path's `is_dir`/`exists`) still run on the supervisor; they happen only for a root that is delivering events.
- **Many clients at once.** One service answers every session on the machine, so the searches of several WrongStack sessions and agents meet in its four native query slots. A search that found them taken failed at once with `QUEUE_SATURATED`, which the WrongStack adapter does not retry: 7 of 20 concurrent searches failed, each of them a few milliseconds of work. A search now waits up to 5 s for a slot (the waiters are bounded by the 64 connections) and only then fails with `QUEUE_SATURATED`. A client turned away because all 64 connections are taken was answered and closed before its first frame was read, so a client that wrote that frame a moment later saw a broken pipe (`os error 232`), which reads as a service that is not running; the service now reads the frame first and the client gets `QUEUE_SATURATED` (retryable) with the reason. Clients do not retry it by themselves.
- **A watcher that does not open says so.** An attach that does not end (a share that holds the open of its root) cannot be cancelled; after 10 s the project's `lastError` says that its root has not opened for watching, until the attach ends.
- **`daemon.health` does not wait for the compatibility worker.** Its inventory includes the worker's `hello`, which was read under the worker's lock, held for the whole of a request; one project's indexing run on the worker (minutes on a large checkout) made the health call of every client wait as long, so the service looked hung. The `hello` is now kept beside the lock (set when a worker starts, cleared when it is stopped or replaced). Requests themselves stay serialized: one worker process.
- **Jobs end.** A job whose execution panics is recorded as failed instead of staying `running` until the next start; recording a job's end is retried when the registry is busy. An admission that fails is a failed attempt of its batch (back-off, then parking) instead of an attempt on every tick. `latest_job` is an index seek; the supervisor asks it for every project every second.

GPUI continuation (2026-11-12): Start also waits for a draining service to finish, then starts a successor and acknowledges success only after authentication. An already-running authenticated instance is retained. The operation is bounded to 30 seconds and does not kill the old job or replay a mutation. Singleton-race exit 3 is retried only when the endpoint is unavailable, with a 500 ms launch interval. Other authentication/protocol errors remain visible. A real actor regression failed before this correction and passes afterward while independently checking the old durable job succeeded. The deterministic drain test uses a debug-only native stall; four other actor cases also run against the shipped release daemon. Rendered GUI acceptance remains separate.

Not changed, and recorded as open: the Windows watcher library reports no error for a zero-length change buffer (an overflow inside the OS), so such a loss is found by the periodic reconciliation, not at once; one compatibility-worker call still holds the worker (and so the other projects on it, and a detach that must close its store) for its whole duration; the per-event path checks still run on the supervisor task.

## WI-ADR-023 — One desktop window: GPUI replaces the Tauri desktop (2026-11-14)

The owner decided on 2026-11-14 that one GUI is enough and that the GPUI window stays: the Tauri/WebView desktop (`crates/wrongindex-desktop`, `wrongindex-desktop.exe`) is retired. This supersedes WI-ADR-008's Tauri framework choice outright, and WI-ADR-019's condition that the source client not replace the installer before tray/search/update parity and manual accessibility/DPI acceptance. The process boundaries of WI-ADR-008 and WI-ADR-019 stay: a separate GUI process, authenticated Rust IPC only, no project code, no SQLite writer, no token in any view model, and closing or crashing the window never stops the service.

- **Parity.** Every Tauri surface moves to GPUI except the tray icon (dropped: GPUI 0.2.2 has none, and a tray would need a new dependency): overview banners, project detail and every project action, the machine index scan, live events, diagnostics export, sign-in start, updates through the sibling CLI, and every service setting applied against `expectedRevision`. Rules the Tauri bridge enforced keep their tests: backup names without path parts, Retry only of this project's failed or canceled index jobs, bounded search terms, fixed method per action.
- **Actor.** Commands run concurrently on the actor's runtime; each ends in exactly one outcome that carries the state it produced (a refresh runs before the outcome is sent, and refreshes are serialized, so an older reading never overwrites a newer one). The window disables a control while a request about it is in flight. Events from `events.subscribe` feed Activity and trigger re-reads; they are never the source of truth.
- **Confirmation.** Rebuild, Remove, Restore, Stop service and Update are confirmed in a native dialog whose first and default button is Cancel, so a stray Enter cancels.
- **Packaging.** Tauri's NSIS bundler stays as a build tool only: `cargo tauri bundle` runs from `crates/wrongindex-gpui` with `mainBinaryName: wrongindex-gpui`, the same `productName` and `identifier`, and `webviewInstallMode: skip`. No Tauri crate is linked. The same product name and identifier upgrade 0.2.0 in place; the template deletes the previous main binary and points the `WrongIndex` shortcuts at the new one. The hooks remove the retired preview shortcut and executable and rewrite a `Run\WrongIndex` value equal to `"<instdir>\wrongindex-desktop.exe" --start-service` to `"<instdir>\wrongindex-gpui.exe" --start-service`.
- **Acceptance.** WebView2/CDP gates have no GPUI equivalent and are retired with that reason; rendered-window, keyboard, accessibility and DPI acceptance remain manual gates and are not claimed by this decision.
